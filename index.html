Report 1 of 6: “Reset password link doesn't work”

Environment
Production · Chrome on Android
Documented policy
Reset links expire 15 minutes after they are issued.

Steps as reported

  1. Requested a password reset email at 09:02.
  2. Opened the email and clicked the reset link at 11:15 — 2h 13m later.
  3. Page shows: “This link has expired. Request a new one.”

User's claim: “The link is broken, please fix it.”

Your verdict
Severity compared with the resolution, not scored

Your answer
Resolution

Reasoning

Password reset tokens are intentionally single-use and time-boxed to 15 minutes from issuance — a standard control against a leaked or forwarded email being replayed later. The user's own timeline shows the link was used 2h 13m after issuance, well outside that window. The system rejected an expired token and returned a clear, actionable message rather than failing silently or exposing an internal error. This is the system working correctly, not a malfunction — the fact that the user is inconvenienced doesn't make it a defect. Confirmed against the documented 15-minute TTL policy.

Reported by — Automated monitoring (order-total anomaly)

Report 2 of 6: “Discount code appears to apply twice”

Environment
Production · checkout, all browsers

Steps as reported

  1. Add an item priced at $80.00 to the cart.
  2. Enter a valid 20%-off code and click “Apply” twice in rapid succession, before the button visually updates.
  3. Order total reflects $51.20 instead of the expected $64.00 — the 20% discount applied twice (36% off in total).
Your verdict
Severity compared with the resolution, not scored

Your answer
Resolution

Reasoning

The “Apply” button isn't disabled or debounced while the request is in flight, so two rapid clicks fire two independent apply-discount calls before the UI reflects the first one. The discount is applied twice, compounding (20% off, then 20% off the already-discounted total), rather than the second call being treated as a no-op or replacing the first — a classic idempotency gap around a non-debounced action. Repro is reliable with any fast double-click, so this isn't a one-off flake. The severity call is genuinely debatable: some teams would call this Critical given the direct, silent revenue loss with zero user-visible error; High is the more defensible default here because there's no data exposure or security breach, and the fix (disable-on-click plus a server-side idempotency check) is small and fast — but the “no error is shown to anyone” part is exactly what makes it dangerous, regardless of the exact label.

Reported by — Support agent (relaying customer complaints)

Report 3 of 6: “Intermittent 500 errors on GET /api/orders”

Environment
Production API · no further detail given

Report as received

“Some customers say the orders page sometimes fails to load. Not sure how often or who's affected. Happens randomly.”

Attached: none — no request ID, timestamp, account ID, or response body.

Your verdict
Severity compared with the resolution, not scored

Your answer
Resolution

Reasoning

There isn't enough here to reproduce or even confirm the defect as described. What turns this into something actionable: (1) one exact timestamp plus the affected account/user ID, so the matching server-side request can be located in logs; (2) the actual response body or error code — “intermittent 500” alone could originate from dozens of unrelated code paths; (3) whether it correlates with a specific query parameter, page size, or date range — a customer with an unusually large order history could be hitting a pagination or timeout edge case that only shows up for them; (4) whether it's really intermittent for one user, or only looks that way because different, unrelated users are each hitting different causes. Filing this now with a guessed severity would send someone chasing the wrong lead. Correct next step: go back to support and request a specific timestamp and account ID from one affected customer.

Reported by — QA exploratory session

Report 4 of 6: “Bio field shows 51/50 at the maximum allowed length”

Environment
Staging · profile edit form, stated limit 50 characters

Steps as reported

  1. Open profile edit, focus the Bio field (UI states a 50-character limit).
  2. Type exactly 50 characters.
  3. Counter reads “51/50” instead of “50/50”; a 52nd character can still be typed.
Your verdict
Severity compared with the resolution, not scored

Your answer
Resolution

Reasoning

Classic boundary-value bug: the displayed counter and the actual input ceiling disagree at the exact limit (49 / 50 / 51), which points to the counter being computed separately from the enforcement check rather than sharing one source of truth. More important than the cosmetic “51/50” text is what it implies — if the counter is wrong at the boundary, the true enforced ceiling needs to be tested directly rather than assumed — the field already accepts a 52nd character, so is there any ceiling at all?. Severity is Low: no data loss, no blocked workflow, the form can still be submitted — but it's a real, 100%-reproducible defect worth fixing, and a good tester follows up on what it implies about enforcement rather than closing the ticket once the visible symptom is explained.

Reported by — End user (mobile worker)

Report 5 of 6: “Can't clock in — app says 'Too early'”

Environment
Production · mobile app, shift scheduled 14:00–22:00
Documented policy
Clock-in opens 15 minutes before the scheduled shift start.

Steps as reported

  1. Arrived at the job site at 13:35.
  2. Opened the app and tapped “Clock In.”
  3. App shows “Too early to clock in”; the button stays disabled.

User's claim: “I'm on-site and ready to work, the app won't let me clock in.”

Your verdict
Severity compared with the resolution, not scored

Your answer
Resolution

Reasoning

Per the documented shift-eligibility rule, clock-in opens 15 minutes before the scheduled start — 13:45 for a 14:00 shift. The attempt was at 13:35, ten minutes before that window opens, so the rejection is the system correctly enforcing a documented business rule. This is an easy one to misjudge under pressure: the user's frustration is legitimate — they're on-site and ready — but “the user is inconvenienced” and “the system has a defect” are different questions. Worth raising separately as a UX suggestion (e.g. a countdown to 13:45 instead of a flat “too early”), but that's a product conversation, not a bug fix.

Reported by — Security-conscious user

Report 6 of 6: “Order details visible by editing the URL”

Environment
Production · web app, authenticated session

Steps as reported

  1. Logged in as User A, opened “My Orders,” clicked order #48213 (belongs to User A). URL: /orders/48213.
  2. Manually changed the URL to /orders/48214 (sequential ID) while still logged in as User A.
  3. Page loaded and displayed order #48214's full details — items, shipping address, and the last 4 digits of the payment card — despite belonging to a different account.
Your verdict
Severity compared with the resolution, not scored

Your answer
Resolution

Reasoning

Textbook Insecure Direct Object Reference (IDOR): the endpoint authenticates that a valid session exists but never authorizes that the requested order actually belongs to the requesting user. Sequential, guessable IDs make this trivially scriptable — no special tooling needed to enumerate every order in the system, exposing shipping addresses and partial payment data at scale. This meets the bar for Critical: real customer PII and partial financial data exposed, no workaround available to the business, exploitable by any authenticated user. Immediate mitigation: an ownership check (order.userId === session.userId) before returning any order resource, on every read path — and audit sibling endpoints (invoices, shipping labels, support tickets) for the same missing check, since this class of bug rarely appears in exactly one place.
